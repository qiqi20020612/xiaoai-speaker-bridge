# LX06 v0.1.9 修复记录（草稿）

开发基线为已发布的 [v0.1.8](https://github.com/qiqi20020612/xiaoai-speaker-bridge/releases/tag/v0.1.8)，对应 main 提交 `824d180`。既有行为与验证边界见 [v0.1.8 说明](lx06-v018.md)。

本 PR 保持草稿，用于修复 v0.1.8 的问题；当前开发版本为 0.1.9，尚有其他待补充修复项。未经另行授权，不合并、创建 Tag/Release 或操作真实 LX06 / Home Assistant。

## TTS 合成阶段取消后仍播报

用户报告真实音箱连续三次出现 HA 已显示 cancelled，但仍然播报，涉及主动播报和文字指令。本轮开发与验证保持离线，未对真实设备或私有脚本做修改。

### 根因与修复

- HA 原先把所有 accepted 都当成本地排队，忽略 Bridge 也会在实际接收后返回 accepted。取消时可能只结束 HA 队列项，完全没有向音箱发送取消。现在以一个不持久化的 dispatched 标志区分；请求发出前即置位，只有明确 busy 拒绝才清除。网络结果不确定时继续按原 ID 查询，不盲目重发。仅本地队列取消不调用设备，派发后取消失败不伪造成功。
- Bridge 原先无条件拒绝取消已启动的 send_text。现在只在明确观测到 synthesizing/playing 后允许取消文字回复，取消前读入已经写出的阶段消息，避免 HTTP 与管道在同一轮就绪时使用旧阶段。意图、Conversation 和上下文更新尚未结束时仍拒绝，不撤销已执行动作、不清理共享上下文。
- Bridge 原先回收父 worker 后就忘记其进程组，忽略 TERM 的残留子进程可能继续合成或启动播放器。现在取消保持原有进程组 TERM 和 20 秒清理宽限；父进程结束后使用 WNOWAIT 保留其 PID，先终止该组残留，再回收，避免 PID 复用或误杀无关播放器。重复取消不重发 TERM、不延后期限；子进程在 exec 前恢复 TERM/INT 默认处理，避免继承 daemon 的停止标志处理器后继续执行。
- 延迟音量恢复是合法的后台任务，不能随残留 TTS 一起停止。既有恢复脚本通过本地 C helper 在独立会话启动，原任务只等待 exec 确认。沿用原 recovery.lock、owner/starttime、Journal/版本及有界重试；正常恢复成功不启动此 helper，无新常驻进程、定时任务或长期状态。

### 验证与边界

先用受控测试复现 HA 未发送取消，以及已取消父进程退出后子进程仍能启动播放器，再增加回归覆盖：

- 本地队列、Bridge accepted、明确 busy、提交中取消、取消确认丢失和重复 request_id。
- 真实本地 HA Client/JobManager → HTTP → C Bridge → Shell → 脱敏豆包/微软/Google 脚本 → 静默播放器，覆盖两个入口的合成与播放阶段。
- 确认提供方、下载与播放器进程结束；合成返回后不启动播放、不进入后续回退；无关播放器与 Bridge 保持存活。
- Conversation 执行中拒绝取消；TTS 尾段取消后已有指令/上下文不重做、不撤销。
- 音量和资源锁恢复、超过六秒的合法清理、重复取消，以及锁占用下延迟恢复跨越 worker 回收。
- ARM/QEMU 覆盖取消收尾和独立恢复启动；完整 CI 继续覆盖 BusyBox/jq 1.6、HA、安装/回滚、Journal、LED、语音和上下文。

这些是受控进程与模拟提供方结果，不是 LX06 播放停止时延或固件验收。真实豆包/回退脚本、驱动尾音、网络取消时机、原地升级仍需后续单独授权复验。

## 文字提交清空与原生 Logbook

两个原生 TextEntity 继续通过既有服务与 JobManager 入队。成功入队后清空输入，以对应实际 Entity ID、实体名称和原上下文调用 `logbook.log`，message 为未经裁剪的完整原文；历史由用户现有 Recorder/Logbook 处理。提交失败不写 Logbook，保留未入队的有效输入；并发拒绝不会覆盖正在提交的输入。日志表示提交成功，后续任务结果仍使用原 status/error/request_id 属性。

保持 Unique ID、自定义 Entity ID、255 字符限制、输入校验和原有任务并发保护，无新实体、按钮或历史数据库。Logbook 作为可选启动顺序依赖，不强制启用；服务异常不会把已入队任务误报失败或重复执行。本项仅修改 HA 集成与测试/文档，不修改音箱端或通信协议。隐私与过滤方式见 [文本输入隐私](acceptance-fixes.md#文本输入隐私)。

回归使用 HA 2026.10 原生 Logbook 服务、Recorder 内存 SQLite 和原生活动查询，覆盖两个入口的完整原文（空白、换行、Unicode、255 字符）、重复提交、入队失败后的保留/重试、后续任务失败反馈、实体改名、Recorder 入库/Logbook 展示过滤、历史保留参数及日志异常/并发。测试仅跳过前端静态资源组件，没有替代 Logbook/Recorder；真实 HA 前端交互仍待后续授权部署验证。

## AirPlay 仅在回复实际播放时避让

原 `text.sh::speak()` 在调用一体化的原 TTS 脚本前就执行 `bridge_duck_begin`，因此合成网络等待期间音乐已经降至 10%。原有 `playing` 阶段是对本次进程及其后代的事后观测，不能用它触发衰减，否则解码器可能已经输出语音开头。

### 局部修改与保护

- 仅在 `announce` / `send_text` 的原 TTS 子进程 PATH 前加入本任务临时的 mpg123/ogg123/aplay 入口。复用现有私有工作目录，保存原可执行路径；不修改原 TTS、miplay、Listener、提供方请求或认证配置。[上游 miplay](https://github.com/duhow/xiaoai-patch/blob/b2b14f9e1e68f2f744a3a58b921bd841504734a1/bin/miplay) 通过 PATH 调用这些解码器，入口沿用原文件及 `-w` 等参数；设备实际副本仍待核验。原生 `voice` 继续原调用方式，不安装入口；LED 实现及调用顺序不变，合成期间保持原处理灯效。
- 解码器入口先同步调用既有 `bridge_duck_begin`，再启动真实解码器并等待其结束。原 argv、文件内容和 stdin 直接传递，不读取、缓存或重编码音频。实际播放完成后复用原 `bridge_duck_restore`，真实解码失败仍将原退出码交回提供方；进入下一提供方的合成前音乐已恢复。
- 音源快照与后续 Journal 的两次 AirPlay 观测仍独立，移到播放前取得当前基线；保留明确 AirPlay-only、未知/冲突不衰减、10% 绝对上限、Volume Lock、Journal 和发送端/通道版本保护。合成期间 HA 或手机的新音量成为播放基线，播放期间的新目标不被旧恢复覆盖；notifyvol 临时覆盖时机保持原样。
- 保留原音频锁、Session 释放顺序和进程组取消。入口的 owner/starttime 与本次工作目录限定生命周期；任务先关闭入口再恢复，持锁等待的迟到入口不能在清理后启动播放。原生语音已经捕获基线、等待远程 Audio Lock 时，不新增迟到衰减；已经存在的 Duck 仍走原语音交接。内层解码器不重复衰减，异常恢复继续使用原 Journal 和有界恢复脚本。
- 音量读取、Journal 写入、锁或衰减失败不启动真实解码器。入口把有限错误码交回父任务，由父任务清理并报告失败；不让这种安全失败被私有 TTS 当作提供方错误再次合成。额外状态只在本任务工作目录，新增进程仅随实际解码器存在；没有新常驻进程、服务、定时任务或长期缓存。

### 自动化与真机边界

受控测试覆盖豆包、微软和 Google 脱敏脚本的两种 HA 入口：阻塞合成时无 master 写入/无 Duck Journal，解码器读取第一个字节前音量为 10%，播放结束恢复；校验原文件/argv、16 KiB stdin 全字节及私有脚本原字节未变。还覆盖回退合成期间的音乐/灯效、HA/发送端在合成与播放期间调音、安全失败不播放/不额外回退、取消时等待 Volume Lock 的迟到入口、嵌套解码器、缺少 `/proc/.../children` 的本次播放状态，以及原生语音准备竞争和不安装入口的隔离验证。原有低音量、未知/多音源、Journal 失败、TERM/KILL 恢复、抢占、LED、上下文及安装回滚断言保留；相关旧测试的注入点从“合成”移至“真实解码器”。

这些是模拟提供方、静默解码器与字节顺序证据，不能证明 LX06 声学首字完整、真实网络耗时或 CPU/内存无回归。LX06 的实际 miplay 是否通过 PATH 调用解码器、真实豆包/私有回退链的文件播放与阻塞等待、异常恢复/语音抢占听感仍需后续授权验证。自定义 TTS 若重置 PATH、绝对调用解码器或另用播放器，不受任务入口覆盖；不据此提前衰减、修改私有文件或宣称适配完成。每次播放增加一个短寿命 Shell 包装，复用原按需查询；本轮未测真机资源占用或报告延迟提升。

## 发送端调音后 Duck 卡在 PENDING

用户报告播报期间从 iPhone 调音，结束后 master 仍为 10%、Duck Journal 保留 PENDING。离线复现确认：旧恢复器发现 AirPlay raw 已变化、硬件仍等于 applied_master 时，无法决定新目标，只能重复保留 PENDING。不能直接删除记录、写回旧 master，或把 AirPlay 控制百分比线性当作 ALSA 百分比。

本项获用户授权后通过 SSH **只读**核对了正在运行的 Shairport 4.3.5：显式 `-c` 配置，`mixer_control_name="mysoftvol"`，`standard` 曲线、30 dB 范围及 -4 dB 上限；该控件 TLV 为 -51 dB 起、0.2 dB 步进。配置文件早于进程启动，`amixer -- get` 语法可用。没有播放、调音、修改配置、重启、安装或上传文件；这些信息是目标模型的静态核对，**不是新恢复代码的真机写入验收**。

### 恢复方式

- 原正常恢复、HA 通道版本优先，以及已经观测到发送端新硬件音量的让出逻辑保持。仅 Duck 的 master PENDING 或其已开始恢复的交接记录进入新分支，不改变录音、LED、TTS 合成/播放入口或 HA 协议。
- 按需加载 `sender-recovery.sh`，从唯一 Shairport 进程的显式配置路径读取小型、受限的普通文件（拒绝符号链接），校验 PID/starttime、4.3.5 版本、当前 D-Bus Profile、配置修改时间及 ALSA 实际 dB TLV。局部 C helper 按上游 [player.c 的硬件范围选择](https://github.com/mikebrady/shairport-sync/blob/4.3.5/player.c)与 [common.c 的 standard/flat 曲线](https://github.com/mikebrady/shairport-sync/blob/4.3.5/common.c)计算当前 D-Bus raw 对应的 centi-dB，再交给 amixer 的原生 dB 接口量化。没有固化本机曲线数值或推测声卡百分比。
- 只写共享的 mysoftvol，不对 Shairport `Volume` 或 `SetAirplayVolume` 发写请求，不把旧 raw 回发 iPhone。写后复查主接口的 raw/Active/Profile/版本和进程身份，并确认 RemoteControl.AirplayVolume 与上游固定两位小数的元数据表示一致；主 raw 仍按完整数值检查，不能用舍入忽略继续调音。上游 [D-Bus 实现](https://github.com/mikebrady/shairport-sync/blob/4.3.5/dbus-service.c)从音量元数据发布后者；单看主 Volume 可能早于实际应用。静音时先确认 Shairport 已应用 -144，才解除本地 cap，保留其软件静音。
- 手机继续调音、写失败、确认超时或进程变化时不删除恢复依据。复用原 Journal 的一个 `sender_recovery` 标志，在硬件写入前原子提交；重试时不能把恢复器自己写出的非 10% 值误认成外部最终目标。该标志随已有 duck→voice 事务传递，新的 HA master 版本仍优先。继续使用现有 Volume Lock、逐通道恢复及按需有界重试，无新常驻进程、轮询器、长期缓存或用户配置。
- 已确认 AirPlay 停止时，仅解除仍由本次恢复拥有的 cap；已有新 master 不回写。查询失败不等同停止。无法证明配置/目标时继续原保守 PENDING，独立 TTS/Bluetooth 通道仍可恢复，显式新 HA master 仍可解除待办。新计算分支限于已校验的默认 ALSA 设备、mysoftvol index 0、无硬件静音、显式且容纳于硬件的 max/range，以及 standard/flat；includes、启动后改配置、其他 backend/mixer/profile、混合软硬件范围或不支持的 TLV 不套用猜测模型。

### 验证与边界

自动化覆盖曲线断点与边界、native/sanitizers、两种 HA 入口、发送端连续调音、元数据舍入、写失败/确认失败后的重试、SIGKILL 发生于写入之后、HA 新版本优先、静音确认、停止、未知配置/观测、合法新目标恰好也是 10%，以及带恢复标志的语音交接。另以固定输入与随机种子对照官方 4.3.5 的 standard/flat 函数，4,008 组 centi-dB 输出一致。旧的“未知发送端目标保持 PENDING”断言没有删除或放宽；新增已知有效共享 mixer 场景验证能够真正结束 Duck。ARM/QEMU 另核验同一模型的 centi-dB 输出；音频与 D-Bus 均为替身。

普通恢复和正常唤醒不增加该 helper、进程/配置查询或确认请求。新增成本只在原本无法恢复的分支，未以主观听感或模拟计时声称真机提速。Shairport 不持有 Bridge 的 Volume Lock，故保留写后确认与已有有界重试；持续变化、异常配置或不可用观测不能承诺立即完成。实际播放中的恢复听感、ALSA 量化、快速滑动、静音/断连、语音抢占和真实负载仍待另行授权部署后验证。升级应使用匹配 C helper 与 Shell 的完整安装包，不手工删除 Journal 或覆盖私有配置。
