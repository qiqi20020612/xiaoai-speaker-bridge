# LX06：0.1.3 → 0.1.5 修复与测试说明

本版以仍在运行的稳定 0.1.3 为升级起点，依据 2026-10-12 只读审计的 F01～F07 和 R01～R15。没有部署 0.1.4，也没有增加专门的 0.1.4 历史降级路径。本轮只修改仓库、在隔离环境测试和发布；没有更改或操作真实音箱、HA。

下表中的“实现/测试”是代码与隔离验证，**不表示 0.1.5 已通过真机功能验收**。原只读审计及证据 JSON 保留在用户本地，不随公开包发布。

## 自动化验证范围

测试样本保留真实 Launcher 的全部函数与调用顺序、LED 1/2/11、录音管道、KWS 监督、完整 AirPlay worker/restore 分支及三种 TTS 的回退结构，删除秘密和设备地址，重建必要的变量表达式。运行时所有硬件路径、播放器、HTTP 和服务均替换为隔离 mock，不执行真实脚本中的业务动作。

故障注入涵盖恢复锁竞争、混音器错误、失败的音频接管、发送端改变及无法判断的 cap、空 STT 提前恢复、KWS 重入、活着但身份/启动时间不符的 PID、OAuth 刷新轮换、安装快照复制失败、空间不足、任务未空闲、Listener 未就绪和已启用 0.1.3 的原样恢复。HA 测试继续覆盖旧实体 registry、上下文 TTL、幂等、取消、优先级和便捷输入。

CI 使用真实 BusyBox 1.36.1 ash/flock/awk/sed，并启用 ash 的兼容语法选项，单独验证只读审计已确认的 substring、let、&>；不能仅比较版本号而忽略编译特性。其余检查包含 HA 2026.10、C 编译及 sanitizers、ruff/clang-format/ShellCheck、HACS、hassfest。ARM 包检查 EABI5 hard-float、静态 ELF、内外 SHA256；QEMU 验证 CLI、配置、认证 HTTP、状态、worker 任务和幂等。QEMU 与 CI 都不证明 LX06 的音频/LED/DBus 驱动功能。

## 人工升级：只走 0.1.3 → 0.1.5

这些是用户后续自行执行的写入步骤，本轮没有执行。

1. 下载 v0.1.5 的 LX06 包、HA ZIP、RELEASE_NOTES.md、SHA256SUMS，先在工作站核验全部外层校验和。保留当前 HA 自定义组件副本和配置备份；不删除集成或实体 registry。
2. 只读复制音箱原始 `/data/porcupine_launcher_kws`、`/data/kws_guard.sh`、`/data/airplay_volume_led` 到工作站私有目录。使用 **0.1.5 工具、Python 3.14** 重新生成并审阅三个私有副本和 review format=3，放进仅供本机部署的包目录 adapter/。不沿用 format=1，不修改原始设备脚本，不上传私有部署副本。
3. 保持新 task_led/announcement_ducking 验证标志和 HA 音乐避让选项关闭。现有已验证能力、enable、UUID/token 保留。当前 0.1.3 没有启用过 AirPlay guard，无须做中间版本移除；若现场实际不同，先审阅当前 guard，再按安装文档处理。
4. 留存本机私有的当前 0.1.3 Bridge 目录、Listener、KWS/OAuth 脚本、Cron/boot 的副本及哈希，权限 0700/0600；这些副本不能公开。不要用旧 Listener 全文件覆盖日后已经刷新过的认证值。
5. 排空 HA 队列，暂停会提交新任务的自动化，保证无人唤醒/调音量；用安全的认证读取方式确认 voice.active=false、audio_active=false、state_stale=false。检查原 Bridge、Listener/KWS 单实例、原语音可用、原源文件哈希不变，且没有 `.new`/`.previous` 或未完成备份事务。
6. 检查 /data、/tmp 和内存。安装器需求为 package KiB + 2×现有 Bridge KiB + 512 KiB，并留额外日志/音频余量；包解压在 /tmp，不能删旧备份腾空间后猜测恢复。
7. 上传审核后的私有部署副本到 /tmp，先在解压目录 `sha256sum -c SHA256SUMS`，再执行 `sh install.sh --dry-run`。预览只使用只读 FD 检查，读取状态/空间/哈希，不创建业务文件、不调用服务；任何拒绝先解决，不绕过 checker。
8. 执行 `sh install.sh --apply`，等待完整退出。不要在仍运行的 /data 安装目录执行安装器。成功应为 backup/status=installed、Bridge version=0.1.5、私有 Listener 初始化及 KWS 单实例就绪，原 enable=true；核验 INSTALLED_SHA256SUMS、review 和 boot 哈希，再做下表基础复验。
9. 安装 HA 0.1.5 并按 HA 正常流程重启/重载，使用现有集成、身份和实体。可以 HA 先升级验证旧协议，但测试新功能前两端都应为 0.1.5；无需安装或验收 0.1.4。
10. 基础功能通过后，单独审阅并启用新版 AirPlay LED guard，再逐一验收新的灯效/音乐避让；测试通过才记录对应 verified，不能一次性打开全部标志。

## 失败恢复

安装器返回非零就停止，不反复执行其他版本。`failed_restored` 表示已尝试恢复当前升级前 0.1.3；核对 **原二进制哈希、私有适配哈希、enable=true、原 include 数量、Listener/KWS 进程、当前 OAuth 及原语音**。不要仅依据状态名宣布功能已恢复。诊断位于 /tmp 的 Bridge log 和 .1；分享前脱敏。

若为 `recovery_required`、`replacing` 或 `prepared`，使用 **同一完整 0.1.5 解压包** 执行 `sh install.sh --rollback`。它不要求旧适配器满足新 format=3，不整份覆盖当前 Listener/OAuth 配置，不修改 KWS/OAuth 原脚本，不触碰原音频服务。保留所有 .failed/.incomplete/.retained 和升级前快照。若无完整快照或原配置被独立改动，应保留现场排查，不强行覆盖。不要用 --uninstall 替代恢复现有稳定 0.1.3。

有序 rollback 能恢复文件和运行选择；掉电、硬件损坏、HA 不可用、永久 I/O 错误不属于已经验证的可恢复前提。若恢复记录仍存在且 `volume_recovery_pending=true`，锁争用解除后会有界重试，后续安全操作也重试。对于发送端目标与 cap 无法区分的情况，用户可重新设置发送端音量，或通过现有 HA master 音量接口明确提交新目标；不要手工删除恢复记录或猜测把 dB 线性换算成 ALSA 音量。
